在快节奏的信息时代中，AI 的作用逐渐提升，人的价值却被忽视。

有相似经历的人走在相似的道路上，好像同一根树枝上的叶子一般，面临着相似的问题，遇到过相仿的困难。

人生是旷野，不是轨道。通向终点的路不止有一条。

## 1. 项目定位与边界

### 1.1 一句话说明

《人生分"枝"》是一款**基于知乎真实经验的行动路径探索工具**：输入你的客观处境与想走的方向，输出前人走过的路径、可参考的做法、相关风险与仍需确认的条件，并对每一条给出可追溯的原文出处。

### 1.2 首发范围

首发聚焦两类高确定性决策场景：

| 场景 | 典型问题 |
|---|---|
| **A · 转专业** | 大学新生想转专业，不清楚要不要转 / 怎么转 |
| **B · 转行 / 转岗** | 行业从业者想转行，想寻找前人经验 |

支持的具体路径包括：校内转专业、跨专业读研、辅修、第二学士学位、转行业·转岗。**超出范围的问题，系统会明确返回"暂不支持"并给出提示，而不是硬凑一个结果。**

### 1.3 边界声明

| 不做 | 原因 |
|---|---|
| 不给人生建议、不替用户作决定 | 我们呈现经验，判断权属于用户 |
| 不做综合匹配分、不显示精确匹配百分比 | 未经验证的精确数字会造成"伪精确"误导 |
| 不做成功率预测、不把提及频次说成因果 | 样本频次 ≠ 成功率 ≠ 因果关系 |
| 不评价用户的选择、不评价某个专业或行业 | 立场中立是产品可信度的前提 |
| 不生成、不补写、不虚构任何经历 | 内容只能来自知乎真实回答 |
| 不用大模型记忆回答人生问题 | 不可核对的答案没有参考价值 |
| 不涉及政治相关内容、不做历史舆论演变、拒绝任何 Prompt 诱导与越权 | 内容安全红线 |

## 2. 核心创作思路与目标用户

> 对应主办方要求：项目的核心创作思路和目标用户

### 2.1 问题：经验存在，但不可用

```
信息不对称   真实经验散落在成百上千条回答里，你刷不完
噪音难辨     机构软文与营销号混在其中，你分不清
背景难对照   别人的条件跟你不一样，参考价值大打折扣
```

这三条问题，每一条都在产品里有对应的工程解法（条件化检索、内容分类与推广识别、条件逐项比对）。

### 2.2 洞察：三个只有真正做过检索才会发现的事实

我们在真实的知乎检索中确认了三件事，它们直接决定了产品的形态：

**第一，关键词分组不可靠。** 实测存在同一条回答同时命中"前景"与"劝退"两组关键词的情况。这说明**内容的倾向必须由内容本身判断，不能由检索词的方向决定**。

**第二，时效性会让正确的内容变成错误的内容。** 例如"早期土木吃香"这类经验，在当时完全正确，放到今天却会误导人。信息流本身不解决这个问题，产品必须**显式标注内容的年代**。

**第三，立场会随视角变化。** 在校生认为行业蒸蒸日上、旁观者认为行业正值夕阳——两者都没有说谎。所以**不能把一篇文章整体贴上"成功"或"失败"的标签**，只能标注它描述的是哪个阶段、哪种立场。

这三个洞察对应三条产品原则：**内容级判断、时效标注、阶段分层**。

### 2.3 一个形象的比喻

有相似经历的人走在相似的道路上，好像同一根树枝上的叶子一般，面临着相似的问题，遇到过相仿的困难。前辈们当年遇到这样的问题时，又何去何从了呢？

**人生是旷野，不是轨道。通向终点的路不止有一条。** 我们不替用户选路，而是把走过的路、以及路上真实发生过的事，尽量完整地呈现出来。

### 2.4 目标用户

- **A · 在校生**：面临转专业抉择，需要知道真实的条件门槛、时间成本与可能的代价；
- **B · 职场人**：考虑转行或转岗，需要知道前人的路径、投入产出与常见的坑。

### 2.5 设计原则

1. **不替用户决定**——所有输出为"经验呈现"，不是"建议"；
2. **正反并置**——值得参考的做法与相关风险同时呈现，不做单侧美化；
3. **一切可追溯**——每条重要结论都绑定来源原文片段，可一键跳转知乎原文；
4. **未知即未知**——信息不足时如实标注"未说明 / 未知"，绝不推断补全。

## 3. 核心体验：用户如何走完全程

> 对应官方要求：用户如何完成核心体验

### 3.1 完整旅程

**第 1 步｜描述你的选择**
首页不直接收集用户信息，而是一个输入框："说说你正在考虑的一个转专业或转行业选择。"用户可以自然地写，例如"非科班，在职，想转行做开发"。页面提供四个示例方向帮助起步。在此之后，根据用户的输入内容匹配下一步关键条件补齐。

**第 2 步｜补齐关键条件**
系统根据描述生成一份**条件表单**（4–6 个问题），并尽量预填已知信息、附上用户原话作为依据。表单覆盖：当前阶段、目标方向、可投入时间、学历/年级、绩点或排名、资源限制、不能接受的代价等。

> 关键设计：**每个字段都提供"不知道 / 尚未核实"选项。** 我们不强求用户填满画像——不知道就说不知道，系统会把它计入"未知"而不是猜一个值。

**第 3 步｜确认路径**
用户可以选择更具体的决策路径（校内转专业 / 跨专业读研 / 辅修 / 第二学士学位 / 转行业·转岗）。这一步**在本地完成，不消耗任何检索额度**。

**第 4 步｜实时检索（可见的过程）**
点击开始后，界面显示三步进度：**检索正反经历 → 整理行动路径 → 核对证据**。同时有一个「本次查询记录」面板，逐轮显示：轮次、用途、检索词、返回条数、累计去重数。

> 关键设计：**把检索过程透明化。** 在此过程中，用户能看到系统查了什么、查到多少、为什么停下来，而不是面对一个黑盒等待动画。

**第 5 步｜结果页：按行动路径组织**
结果不是一堆文章列表，而是**行动路径导航**：

- 左侧为从真实证据中提取的行动路径，右侧为所选路径的详情；
- 每条路径下有「**路径依据**」，按 7 类证据分组：行动 / 建议 / 条件 / 成本 / 结果 / 政策 / 统计；
- 每个个案卡展示：**背景 · 行动 · 阶段结果 · 结果状态**；
- 可展开「**条件比对**」，逐项列出你与当事人的条件**相似 / 不同 / 未知**及各自依据；
- 结果可按状态筛选：全部 / 正向 / 受挫 / 有得有失 / 结果未明。

**第 6 步｜本次研究覆盖**
页面提供一块「**本次研究覆盖**」汇总：来源数、去重数、采纳案例数、路径数、以及**明确列出的信息缺口**。系统还会区分**通用模式**（条件不全，只能给一般性经验）与**个性化模式**（关键条件齐全，可做条件化比对）。

> 关键设计：**主动暴露自己的不足。** 覆盖面板会诚实告诉用户"这个方向我们只找到 3 个有效来源"，而不是假装结论很扎实。

**第 7 步｜官方材料补充（转专业场景）**
当用户提供学校或政策链接时，系统会抓取学校官网 / 政府站的 HTTPS 页面及同站附件（PDF / DOCX），做年份与时效校验，并标注政策状态：**现行 / 已过期 / 不同年份 / 未知**。

> 这一步的意义：知乎经验回答"别人是怎么做的"，官方材料回答"规则到底怎么规定的"。**两者分层呈现，不混为一谈。**

**第 8 步｜招聘要求校准（转行场景）**
用户可粘贴最多 5 条真实招聘 JD，系统比对学历、年限、作品、技能、执照等要求，让"转行可行性"落地到具体门槛。

**第 9 步｜动态补问（零成本即时响应）**
当系统发现某个条件是判断适用性的关键、而你还没提供时，会发起动态补问（最多 8 个问题）。每个问题都附带**来源引文**和「查看相关经历」跳转，让你明白"为什么问这个"。

> 关键设计：**补答后不重新检索、不重新调用模型。** 系统直接在已有证据上做本地重算，实时更新结果——这让追问体验是即时的，也让额度消耗是零。

**第 10 步｜保存与比对**
研究结果可保存到服务端，支持打开、删除、以及与同一问题的另一版本做差异比对（列出变化的条件项）。浏览器端另有一份本地快速历史（每台设备最多 20 条）。

**第 11 步｜反馈**
结果页提供 1–5 星评分与可选评论，进入数据后台供团队分析。

### 4.2 检索管线：五轮条件化检索

每次新研究执行 **5 轮**检索，每轮取 10 条，理论上限 50 个来源。

| 轮次 | 用途 | 检索策略 |
|---|---|---|
| 1 `hard_path` | 命中路径与硬条件 | 决策路径词 + 目标专业/岗位 + 硬性条件 |
| 2 `adaptive_gap` | 自适应补缺口 | 根据第 1 轮已获来源**动态改写**查询词 |
| 3 `outcome` | 结果视角 | 准备 / 入门 / 申请条件 / 招聘 |
| 4 `constraints` | 成本与限制视角 | 补修学分 / 作品面试 等 |
| 5 `retrospective` | **回溯与劝退视角** | 后悔 / 转回 / 薪资 / 空窗 |

设计要点：

- **第 2 轮起自适应**：不是预设 5 条固定查询，而是依据已经拿到的来源调整方向，优先补"证据缺口"；
- **去重按内容**：同一篇文章在不同轮次被召回只计一次，归属由内容判断决定，**不由检索词方向决定**；
- **提前停机制**：5 轮用尽，或**连续 3 轮无新增有效来源**即停止，并向用户明确说明"这**不代表**信息已经完整"；
- **只保留知乎来源**：非 HTTPS、非 zhihu.com 域名的结果直接丢弃。

### 4.3 核心设计一：证据即约束（本项目最重要的工程主张）

大模型会编造，也会"过度推论"。我们把**"结论必须绑定原文"做成了代码级约束**，而不是靠提示词请求模型自觉：

**① 模型不允许自由撰写引文。**
模型不输出引文文本，只输出**片段编号**（`excerptIndex`）。系统拿到编号后，从自己手里的片段数组中取出**原文**替换进去。编号缺失或越界，引文直接置空。

**② 引文必须真的存在于来源里。**
`evidence()` 校验引文长度 ≥5、且必须是该来源片段数组的**子串**，否则丢弃。

**③ 摘要必须过第二次独立复核。**
抽取完成后，会发起**第二次独立的模型调用**，逐条判定：该摘要是否被引文支持（`supported`），以及内容类型是否正确（背景 / 行动 / 结果 / 做法 / 风险需一一对应）。
本地还会先做一轮规则预筛：摘要里的数字、百分比、带单位数量、学历词、频率表述、里程碑词必须都能在引文里找到；引文有否定词不能被丢掉；不能引入"因此 / 导致 / 保证 / 必然 / 成功率"这类因果或绝对化措辞。

**④ 未通过的结论不进结果页。**
所有复核未通过的案例会被**直接移除**。界面上，未通过复核的内容**不会**被当作摘要展示，而是显示"**暂未形成可靠归纳**"并保留原文折叠——**宁可什么都不说，也不把原文引用伪装成结论。**

> 这一条直接回应了官方提交检查第 7 条（不把"代码完成"说成"线上可用"）的精神：**我们同样不把"有原文"说成"有结论"。**

### 4.4 核心设计二：立场、行动、阶段结果三分

把一篇文章整体判成"成功"或"失败"是最常见的错误。我们做了三件事：

**① 受控阶段枚举。**
- 转专业：4 个成功阶段（具备申请资格 / 考核通过 / 转出获批 / 转入完成）+ 3 个受挫阶段（不具备申请资格 / 考核未通过 / 转出被拒）
- 转行：4 个成功阶段（获得面试 / 拿到 offer / 入职目标岗位 / 通过试用）+ 2 个受挫阶段（面试被拒 / 求职后无 offer）

**② 每个阶段带范围声明。**
例如"转入完成"明确标注：**只证明已转入目标专业，不证明后续适应、毕业或就业结果。**
系统禁止"转入成功 ⇒ 后续一定顺利"、"学习/做项目 ⇒ 已入职"这类跨阶段推论。

**③ 识别不出就标未知。**
阶段校验会检查：引文是否为原文、成功阶段是否存在否定词、是否混入意图词（想/希望/计划/准备/目标/如果/为了）、是否有第一人称或终局标记（我/本人/最终/后来/已经/成功/未能/被拒）。**任何一项不满足就不给阶段结果**，标记为"结果未明"，**不自动归类为成功或失败**。

> 立场（作者看好/劝退/中性）、行动（做了什么）、阶段结果（走到哪一步）是三个**独立字段**，不混同。

### 4.5 核心设计三：条件比对，不给总分

**比对维度**（按决策路径不同）：

| 路径 | 比对维度 |
|---|---|
| 转专业 | 12 项：每日时间、每周时长、当前阶段、当前学期、绩点、排名百分位、排名位次、挂科数、补修学分、申请截止、转专业限制、政策核实状态 |
| 转行 | 10 项：每日时间、每周时长、相关工作年限、当前学历、投递数、面试数、收入空窗月数、作品/作品集、收入连续性、是否接受入门岗 |

**输出形式是等级，不是分数**：每一项给出「**相似 / 不同 / 未知**」，并附用户值与当事人值及各自引文。

比对前有**兼容性闸门**：字段、单位、语义类型必须一致；绩点要求双方量表（4/5/100）都能解析且**相同**；排名要求**同一个比较总体**（班级/专业/年级）。不可比就判"未知"并说明原因。

**不做综合分**——每一项的结论都附一句提醒："这一项的可核对条件相同，不代表整体条件相同。"

### 4.6 预算、缓存与降级

**调用预算**（写在常量里，硬约束）：

| 阶段 | 次数 |
|---|---|
| 检索 | 5 次（每轮 10 条） |
| 条件表单生成 | 1 次 |
| 分析（抽取 + 摘要复核 + 路径证据复核） | **典型 3 次，最坏 7 次** |
| **复用来源重算（动态补问 / 改条件）** | **0 次检索、0 次模型调用** |

**缓存分层**：

| 层 | 策略 |
|---|---|
| 内存 | TTL 1 小时，上限 40 条 |
| SQLite（持久） | TTL 24 小时，1000 行，累计上限 64 MiB，文件权限 0600 |
| 旧 JSONL | 只读回填，不追加、不自动删除 |

缓存键为查询词的 SHA-256 摘要。**缓存读写失败不影响主流程**，一份有效的检索结果绝不会因为缓存写不进去而丢失。

**节流与配额**：

- 检索请求**串行执行**，两次之间至少间隔 1.8 秒；HTTP 通道超时 60 秒；
- 服务端预算闸门：全局 **50 次搜索 + 100 次模型调用/日**；单客户端 **10 次搜索 + 20 次模型调用/日**、**6 次请求/分钟**；
- 同时进行的探索上限 2 个；作业保留 1 小时、上限 30 个。

**降级与异常处理**（对应官方提交检查第 6 条）：

| 故障 | 处理 |
|---|---|
| 未配置检索凭证 | 自动回退到本地 CLI 通道 |
| CLI 不存在 | 返回带**具体路径与设置指引**的中文错误，而不是裸报错 |
| 额度耗尽 / 触发限流 | 明确提示额度状态，**保留已取得的来源** |
| 缓存损坏 / 解析失败 | 忽略缓存，继续检索 |
| 模型输出非合法 JSON | **仅一次**格式修复重试；修复仍失败则保留来源并提供"复用来源重试"；格式错误记录**脱敏后**落盘（不含提示词、正文、密钥） |
| 摘要复核失败 | 保留引文，但**不作为结论展示** |
| 路径证据整理失败 | 保留全部已复核案例，提示"可复用现有来源重新分析" |
| 有效案例过少 | 触发**一次性有界恢复**（不重新检索、不再递归）；仍不足则如实展示 |
| 检索结果为空 | 返回空态页并提供可重试入口 |
| 分析失败 | 明确报错，**不静默替换为虚构案例** |

> **贯穿全管线的一条原则：任何降级都不会伪造内容。**

### 4.7 云端部署形态

Demo 部署在阿里云（Ubuntu 24.04）。这里有一个值得记录的工程决策：

服务器可用内存仅约 **1000 MB**，`npm ci` 多次被 OOM 杀掉（即使加了 2G swap）。因此我们最终采用**免安装部署**：

1. 依赖只在本地安装并完成构建（`dist` 产物平台无关，仅约 **1.2 MB**）；
2. 上传 `dist` 到服务器解压；
3. `standalone-server.mjs` 只依赖 Node 内置模块 + `dist`，**不需要 `node_modules`**。

该入口用**与本地开发完全同一份**后端中间件，同时提供页面（含 SSR）、静态资源与 `/api/branches/*` 接口，单端口对外。进程由 systemd 守护，**开机自启**。

**安全边界**：知乎凭证与模型密钥**只存放在服务端**，不进入前端、URL、日志或代码仓库；生产环境使用 `__Host-` 前缀 + `HttpOnly` + `Secure` + `SameSite=Strict` 的会话 Cookie 做用户隔离；请求体有体积上限；跨站请求被拒绝。

### 4.8 质量保障

我们为"分析质量"建立了可回归的评估体系，而不是只靠人工观感：

- **40 例人工评估集**：转专业 20 例 + 转行 20 例，每类各覆盖 6 种场景（条件充足 / 条件不足 / 条件冲突 / 单侧证据 / 推广内容 / 结果未明），并断言系统给出的路径与领域分类正确；
- **35 个测试文件、约 218 个测试**：覆盖引文绑定（断言"模型改写的引文**绝不会**被采用"）、案例召回与恢复、检索相关性、条件比对、阶段结果校验、证据策略、降级路径、管理鉴权、生产会话隔离等；
- **5 个浏览器端测试**（Playwright，1440 / 390 / 360 px）：断言**未通过复核的内容绝不以摘要形式呈现**、结果页不出现横向溢出、条件草稿在中断后不丢失且以"复用来源"方式重新提交；
- **人工实时验证脚本**：在真实额度下跑端到端流程。

我们同时明确：**这套评估不证明来源真实性，也不证明模型抽取在真实数据上的准确率。** 相关边界已写进仓库的评估报告，供评审查阅。

## 5. 知乎开放能力使用说明

> 对应官方要求：使用了哪些知乎开放能力

### 5.1 能力清单（如实）

| 知乎能力 | 在本项目中的用途 | 状态 |
|---|---|---|
| **知乎搜索 `zhihu_search`** | **唯一内容源**：五轮条件化检索真实回答与文章 | ✅ **生产使用**（当前额度 5000/日） |
| 知乎直答 `zhida_openai` | 早期曾用作分析引擎 | ⛔ **已弃用**（额度与长上下文分析成本不匹配，改用 DeepSeek V4 flash） |
| 黑客松故事 / 知识内容 API | 作为结构化知识补充源 | ⛔暂不考虑使用 （**当前未接入**） |
| 知乎 OAuth | 账号登录、读取授权用户的公开数据 | ⛔首demo版接登录*降低使用门槛） |

### 5.2 我们如何理解"使用开放能力"

我们只用了**一个**知乎内容能力，但把它用到了足够深：

- **不是单搜索**：而是**五轮、带自适应改写、带去重、带提前停判定**的条件化检索；
- **不是回即用**：而是对每条来源做内容分类（个人自述 / 转述 / 建议 / 推广 / 未知）、时效抽取、推广识别；
- **不是离平台消费**：每一条结论、每一项成本、每一个做法，最终都回链到知乎原文。

### 5.3 检索与分析解耦

这是本项目的架构主张，也解释了为什么分析引擎的更换不影响产品定位：

> **知乎负责"说什么"，模型只负责"怎么组织"。**

- **内容侧 100% 来自知乎**：模型不接触任何其他内容源，也不允许写检索词之外的内容；
- **模型侧只做结构化**：把已存在的经验抽取为行动、条件、成本、结果等字段；
- **可替换性**：分析引擎是可插拔的（早期用知乎直答，现用 DeepSeek）；**即使替换引擎，产品呈现的仍是知乎的经验**。

我们把这一条视为对知乎生态负责的设重要计：**换了模型，产品依然是知乎内容的呈现方式。**

## 6. 与知乎社区生态的契合度

> 对应官方要求：项目与知乎社区生态的契合点

### 6.1 内容层：做"经验的再组织"，不做"经验的再生产"

产品全程**不生成任何新经历**，只对知乎已有的真实回答做结构化整理。所有分析产物都能一键回到原文。

与通用 AI 问答的分界在这里：后者用模型参数中的模糊记忆回答人生问题，**不可核对**；本项目用**可点开、可核对、带赞同数与发表时间的社区原文**回答。

项目文档中有一句话，是产品的原话，也是我们的立场：

> **"你可以询问任何关于人选择问题，而我们则不会给出建议，而是会将前人的经验尽数呈现在你眼前。"**

### 6.2 机制层：复用社区已有的质量信号，
我们没不明一的权威标准，而是**复用知乎社区自身积累的信号**：

| 社区信号 | 我们的用法 |
|---|---|
| 赞同数 | 参与来源排序，作为代表性参考 |
| 作者认证 / 机构标识 | 与内容分类双通道识别推广内容；认证 ≠ 推广，需双重印证才剔除 |
| 发表 / 编辑时间 | 抽取内容年代，**显式标注时效**，解决"早期土木吃香"式误导 |
| 第一人称叙述 | 明确"第一人称**不等于**已核实亲历"，内容类型单独标注 |

在早期真实检索验证中，我们实测到某个品牌的推荐内容由**已认证机构号**发布——这类内容会被标注来源性质，**不作为独立用户案例并列比较**。

### 6.3 流量层：结论即入口，闭环回社区

产品的每一条做法、每一项风险、每一个路径结论，最终都指向知乎原文链接。用户点击即可跳转阅读、点赞、关注原作者。

**产品不是把内容搬走，而是把原本散落在大量回答里的经验，重新分发回它们的作者。**

> **可验证承诺：本产品不提供任何脱离知乎原文的独立结论。**

### 6.4 价值层：让长尾优质回答重新被看见

知乎大量优质经验回答随着时间推移沉入信息流底部。但"沉底"不等于"过时"——一篇几年前的高赞回答，可能恰好精准命中某类用户的处境。

条件化检索做的事，就是**让这些沉寂的经验按"处境匹配"重新浮现**，并带着原文链接重新获得阅读。

这对**答主**尤其有意义：他们过去写下的经验，会因为新的用户提出相似的问题而**持续被需要**，而不是在一次信息流曝光后归于沉寂。

我们把这件些括为：**存量优质经验的条件化再发现。**

### 6.5 治理层：与平台内容安全同向的红线

产在我们的品文开发档里明确写有"写给 AI 的警告红线"，这在开发期间明确红线，些约束本也是平台内容安全要求同向的动作：

- 不涉及政治相关内容；
- 拒绝任何 Prompt 诱导与越权行为；
- 不做历史舆论演变；
- *擅自评价用户的选择*
- *擅自评价某个专业或行业*
- 不做个性化"建议打分"。

在工程侧我们还也动动我约束：

- **不做综合匹配分***避免伪精确）；
- **不用正反结果数量估计成功率**；
- **不把作者自述当作已确认的因果**；
- **不把未通过复核的摘要作为结论展示**。

我们把认为这是**主动放弃的能力**"。在一个人人都在比拼"AI 能多说点什么"的赛道上，我们认为**知道什么不该说**同样重要，甚至更重要。

### 6.6 可延伸的生态连接

- **黑客松故事与知识内容接口**：可作为结构化知识补充源，与用户经验形成"经验 + 知识"的双层结构；
- **知乎 OAuth**：可接入账号体系，让用户保存与同步自己的研究记录。

以上均为**下一步计划**，当前版本尚未接入。

## 7. 场景价值

> 对应主办方要求：项目对社区用户的实际价值

### 7.1 对提问的用户

| 价值 | 具体体现 |
|---|---|
| 降低信息成本 | 将"刷几百条回答"压缩为"对照一组行动路径" |
| 避免幸存者偏差 | 值得参考的做法与相关风险**同时**呈现 |
| 背景可对照 | 逐项比对"你与当事人"的条件相似 / 不同 / 未知，并说明依据 |
| 结论可核对 | 每条重要结论都能展开到原文片段并跳转知乎 |
| 未知被显式列出 | 影响判断但缺失的条件会被列为"仍需确认"，并在旁栏与用户确认 |
| 决策可执行 | 输出的是路径与做法，而非建议 |
| 提问成本低 | 不知道的条件可以留空；补答后**即时重算** |

### 7.2 对答主

- 长尾回答被**条件化重新检索到**，优质经验的生命周期被延长；
- 每一条被采纳的经验都带回原文链接，**带来新的阅读与互动**；
- 产品明确标注来源与作者，**不改写、不冒充**。

### 7.3 对知乎平台

- **提升存量内容的使用深度**：同一批内容被用于"做对照"而不只是"找一条答案"；
- **提升长尾内容的消费与再发现效率**：让低曝光但高相关的回答重新进入消费路径；
- **开放平台能力的示范应用**：展示 `zhihu_search` 在真实高频决策场景中的一种深度用法（多轮、自适应、可追溯），而不仅是关键词调用；
- **站外导流入口**：每个结论都回链站内，形成从外部决策场景到知乎社区的流量回路；
- **合规与安全同向**：产品的红线设计与平台内容安全要求一致，减少监管与内容风险。

### 7.4 与替代方案的差异

| 维度 | 通用 AI 问答 | 知乎信息流 / 搜索 | **本项目** |
|---|---|---|---|
| 内容来源 | 模型参数记忆，不可核对 | 社区原文，但分散且无结构 | 社区原文，**结构化且可回链** |
| 立场呈现 | 通常收敛为单一建议 | 各条回答各说各话 | **多条行动路径并置**，立场与阶段分层 |
| 条件可比性 | 不感知用户处境 | 不感知用户处境 | **条件逐项比对**，未知如实标注 |
| 时效处理 | 无标注 | 旧内容沉底 | **显式标注内容年代与政策时效** |
| 噪音处理 | 不适用 | 需用户自行辨别 | **内容分类 + 推广识别** |
| 结论性质 | 替代用户思考 | 需用户自行归纳 | **呈现经验，不替用户决定** |
| 可验证性 | 低 | 高但费时 | **高且低成本**（一键回链原文） |









**一句话总结价值**：把知乎"已经有人回答过"这件事，从**可遇不可求**变成**可按处境检索、可对照、可核对**

**注**：以上对比仅代表典型替代方案，不面对所有方案，不能代表所有方案与本方案的差异

| 环节 | 约束 |
|---|---|
| 引文来源 | 模型只输出片段编号，系统替换为原文；编号越界即置空 |
| 引文校验 | 必须是来源片段的子串，长度 ≥5 |
| 摘要复核 | 第二次独立模型调用判定"有据 + 类型正确"；本地预筛数字、单位、学历词、频率、里程碑、否定词、因果词 |
| 未通过处理 | 不作为结论展示，仅显示"暂未形成可靠归纳"并保留原文 |
| 阶段结果 | 受控枚举 + 范围声明；识别不出标"结果未明"，不自动判成功/失败 |
| 条件比对 | 字段/单位/语义类型必须兼容；绩点需同量表，排名需同总体；输出等级不给总分 |
| 内容分类 | 个人自述 / 转述 / 建议 / 推广 / 未知，分别标注 |
